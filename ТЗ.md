Да. И я бы немного **переосмыслил архитектуру**: ты фактически делаешь не просто «загрузчик файлов», а **локальный Data Engineering Workbench** — что-то между подготовкой данных, mini-ETL и визуальным staging/ODS.

И твоя связка **Rust + Dioxus + Polars + Arrow + Parquet** для этого очень хорошо подходит.

### Сначала главное про форматы

Да, в 2026 году **Parquet — один из основных стандартов для аналитического хранения табличных данных**. Это колонночный формат, ориентированный именно на эффективное хранение и чтение аналитических данных. ([Parquet][1])

Но важно разделить:

**Parquet ≠ Arrow.**

Я бы строил систему так:

```text
CSV / Excel / Parquet
          │
          ▼
       Polars
          │
          ▼
   Arrow / Polars DataFrame
      (в памяти)
          │
          ▼
      Parquet
      (на диске)
```

Arrow — это прежде всего **колоночное представление данных в памяти**, а Parquet — **формат хранения на диске**. Они специально дополняют друг друга. ([Apache Arrow][2])

Именно поэтому для твоего приложения я бы **не пытался создавать "Arrow-файлы" как основной результат**.

# Как я вижу твою систему

Представь:

```text
                    ПРОЕКТ
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Продажи     Клиенты      Товары
          │           │           │
       25 файлов    8 файлов    14 файлов
          │           │           │
          ▼           ▼           ▼
       Polars       Polars       Polars
          │           │           │
          ▼           ▼           ▼
   sales.parquet clients.parquet products.parquet
```

То есть **папка в UI становится логическим Dataset/Source**.

Например:

```text
Проект: Продажи 2026

Sources

├── Продажи
│   ├── sales_01.xlsx
│   ├── sales_02.xlsx
│   ├── sales_03.xlsx
│   └── ...
│
├── Клиенты
│   ├── clients_01.csv
│   ├── clients_02.csv
│   └── ...
│
└── Товары
    ├── products_01.parquet
    ├── products_02.parquet
    └── ...
```

Пользователь говорит:

> Вот эти 20 файлов являются одной таблицей `sales`.

Программа:

1. сканирует файлы;
2. определяет формат;
3. читает через Polars;
4. определяет/предлагает schema;
5. проверяет совместимость файлов;
6. приводит типы;
7. объединяет;
8. пишет единый Parquet Dataset.

# А вот здесь есть важный нюанс

Я бы **не обязательно делал один огромный `.parquet` файл**.

Лучше сделать:

```text
data/
└── sales/
    ├── part-00001.parquet
    ├── part-00002.parquet
    ├── part-00003.parquet
    └── ...
```

То есть **Parquet Dataset**.

Например:

```text
sales/
    year=2026/
        month=01/
            part-001.parquet
            part-002.parquet

        month=02/
            part-003.parquet
            part-004.parquet
```

Это гораздо ближе к настоящему Data Engineering.

Parquet официально поддерживает сценарии с partitioned datasets, а Polars входит в число реализаций с поддержкой Parquet. ([Apache Arrow][3])

# ТЗ — Data Engineering Workbench

## 1. Цель

Создать кроссплатформенное приложение на Rust для визуального управления первой стадией Data Engineering pipeline:

```text
Raw Files
   ↓
Schema
   ↓
Validation
   ↓
Normalization
   ↓
Parquet Dataset
   ↓
ODS / DWH / Database
```

Первая версия концентрируется на:

> **File → Schema → Validate → Normalize → Parquet**

# 5. Pipeline

Главный экран я бы строил вокруг pipeline.

```text

  │
  ▼
READ
  │
  ▼

  │
  ▼
VALIDATE
  │
  ▼
TRANSFORM
  │
  ▼
```

Причём каждый блок кликабельный.

```text
       │
       ▼

│             │
│ 37 → 1,2M   │
│ rows        │
└──────┬──────┘
       │
       ▼
┌─────────────┐
│   SCHEMA    │
│ 12 columns  │

└──────┬──────┘
       │
       ▼

│   PARQUET   │
```

# 6. Что происходит при импорте

Допустим:

```text
sales/

sales_01.xlsx
sales_02.xlsx
...
sales_50.xlsx
```

Приложение **не должно сразу грузить все 50 файлов в RAM**.

Лучше:

```text
scan files
     ↓
inspect metadata
     ↓
lazy scan
     ↓
schema validation
     ↓
stream/chunk processing
     ↓
Parquet
```

Polars здесь особенно хорошо подходит.

# 7. Схема должна быть общей

Очень важная часть твоей идеи.

Допустим:

```text
sales_01.csv

id       integer
date     string
amount   float
```

а:

```text
sales_02.csv

id       integer
date     string
amount   string
```

UI должен показать:

```text
⚠ Schema conflict

amount

Expected:
Float64

Found:
String

Files affected:
sales_02.csv
sales_17.csv
sales_23.csv

[Convert to Float64]
[Move invalid rows to quarantine]
[Ignore file]
```

Вот здесь приложение уже начинает становиться **реальным Data Engineering инструментом**, а не красивым файловым менеджером.

# 11. Arrow

Внутри приложения:

```text
CSV
 ↓
Polars
 ↓
Arrow memory
 ↓
Polars transformations
 ↓
Arrow
 ↓
Parquet
```

Arrow здесь становится **внутренним языком табличных данных**, а не конечным форматом хранения. Это именно то, для чего он предназначен: стандартизированное колонночное представление в памяти и быстрый обмен данными. ([Apache Arrow][2])

> **«Я дал программе папку с 50 грязными Excel/CSV/Parquet файлами → программа определила структуру → я подтвердил схему → она провалидаировала файлы → объединила их → получила нормальный Parquet Dataset → показала мне проблемы».**
