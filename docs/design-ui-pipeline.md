# Дизайн интерфейса: пайплайн «сырьё → схема → правила → ODS + карантин»

> Спецификация UI для `strata-web` (axum + askama + htmx + Tailwind).
> Цель: **максимально понятный путь от папки с файлами до чистого ODS**, где
> каждый шаг виден, обратим и объяснён. Документ описывает экраны, состояния,
> тексты и технику сборки на htmx; реализуется по фазам (§11).

---

## 1. Принципы интерфейса

1. **Одна сущность — одна страница.** Всё про `sales` живёт на `/w/{ws}/e/sales`:
   файлы, схема, правила, результат, карантин, логи. Пользователь не «ходит по
   разделам приложения» — он ведёт одну таблицу от грязного файла к ODS.
2. **Состояние видно без кликов.** В списке сущностей у каждой — статус по
   четырём стадиям. Понятно, где мы застряли, не открывая карточку.
3. **Каждое действие показывает последствия до применения.** Инференс схемы,
   правила и stage всегда имеют «проверить на образце» с числами: сколько строк
   пройдёт, сколько уйдёт в карантин и почему.
4. **Ничего не пишем молча.** Несоответствующий файл/строка не «теряется»:
   она попадает в отчёт или карантин с причиной. Это сквозное правило движка,
   и UI обязан его показывать.
5. **Три переключателя вместо сорока настроек.** На уровне воркспейса —
   `execution`, `preview_upload`, `cache_encryption`; всё остальное — по делу,
   в контексте колонки или правила.
6. **Долгие операции — фоновые и видимые.** Прогон в фоне, прогресс-бар,
   лог доступен во время выполнения, страница не блокируется.
7. **Ошибка = «что делать».** Сообщение всегда содержит причину и следующий шаг
   («amount: ожидали f64, в файле str → [Привести к f64] [В карантин] [Пропустить файл]»).
8. **Без JS-состояния.** Никаких «умных» клиентских виджетов: серверные
   фрагменты, поллинг только для прогресса. Один JS-остров появится позже — для
   грида на миллион строк (§10).

## 2. Карта экранов (information architecture)

```text
/                                  Список воркспейсов (+ вход/регистрация)
└── /w/{ws}                        Pipeline home: таблица сущностей и стадий
    ├── /w/{ws}/e/{entity}         Страница сущности (главный экран работы)
    │   ├── ?tab=files             Стадия 1: Файлы и превью
    │   ├── ?tab=schema            Стадия 2: Схема
    │   ├── ?tab=rules             Стадия 3: Бизнес-правила и ограничения
    │   ├── ?tab=ods               Стадия 4: ODS, карантин, передача
    │   └── ?tab=logs              Логи прогонов сущности
    ├── /w/{ws}/runs               История прогонов (все сущности)
    ├── /w/{ws}/runs/{run_id}      Один прогон: фазы, файлы, решения, время
    ├── /w/{ws}/quarantine         Сводный карантин по воркспейсу
    └── /w/{ws}/settings           Настройки воркспейса (3 переключателя + quotas)
```

Почему так: стадии — это **табы внутри сущности**, а не пункты меню. Меню
верхнего уровня остаётся маленьким (воркспейсы / прогоны / карантин / настройки),
поэтому интерфейс не «размазывается» по разделам.

## 3. Экран `/w/{ws}` — Pipeline home

```text
┌ Workspace: Продажи 2026 ────────────────────────────── [Настройки] [Прогоны] ┐
│ источник: /data/sales (allowlist)      исполнение: local                      │
├───────────────────────────────────────────────────────────────────────────────┤
│  Сущность     Файлы   Схема        Правила    ODS                     Действия│
│  sales        ●8      ✔ 12 колон.  ✔ 5 прав.  ✔ 23 стр. 3 части      [Открыть]│
│  clients      ●3      ⚠ конфликт   —          —                      [Открыть]│
│  products     ●0      —            —          —                      [Открыть]│
├───────────────────────────────────────────────────────────────────────────────┤
│  [+ Сущность из папки…]   [Сканировать корень…]   последний прогон: 2 мин назад│
└───────────────────────────────────────────────────────────────────────────────┘
```

* `●8` — файлов в папке; `✔/⚠/—` — готово / есть проблема / не начато.
* Клик по строке открывает страницу сущности на **первой незавершённой стадии**
  (умный вход: пользователь не выбирает таб вручную).
* Пустое состояние: крупная подсказка «Укажите корень, где каждая подпапка —
  отдельная таблица» + кнопка; и альтернатива «Указать папку одной сущности».

## 4. Стадия 1 — Файлы (`?tab=files`)

```text
┌ sales · Файлы ────────────────────────────────────────────────[Схема →]──────┐
│ Папка: /data/sales            [Пересканировать]                              │
│ Параметры чтения:  Кодировка [Авто▾]  Разделитель [Авто▾]  ☑ первая строка — │
│                    заголовки      ⓘ определено: windows-1251, ';'            │
├──────────────────────────────────────────────────────────────────────────────┤
│ Файл            Размер   Строк   Прочитан как           Статус               │
│ sales_01.csv    12 КБ    1 204   CSV · ';' · cp1251      ✔ ok               │
│ sales_02.csv    11 КБ    1 180   CSV · ';' · cp1251      ✔ ok               │
│ sales_03.csv    4 КБ     320     CSV · ';' · cp1251      ⚠ типы (см. схему) │
├──────────────────────────────────────────────────────────────────────────────┤
│ Превью sales_01.csv (первые 50 строк)                                        │
│  id │ date       │ amount │ customer                                        │
│  1  │ 2026-01-05 │ 12.50  │ ООО Ромашка                                     │
└──────────────────────────────────────────────────────────────────────────────┘
```

Правила экрана:

* **Автоопределение по умолчанию**, но с явной строкой «определено: …» — чтобы
  пользователь видел, *как* прочитан файл (это же попадает в логи).
* Смена параметров → кнопка **[Применить и перечитать]**, которая перерисовывает
  список и превью (htmx-фрагмент). Ошибка чтения показывается строкой в таблице,
  а не «красной страницей».
* Статус файла заранее показывает, будет ли он проблемным на стадии схемы:
  это экономит один круг «сходил в схему — вернулся».
* Скачивание: «сохранить превью как CSV» (мелочь, но снимает вопросы «а точно
  так прочиталось?»).

## 5. Стадия 2 — Схема (`?tab=schema`)

### 5.1. Формат схемы: решаем окончательно

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **TOML `*.schema.toml`** | комментарии, строгий парсинг, уже используется, легко диффить в git, вмещает правила/опции чтения | SQL-люди его «не узнают» | **источник истины** |
| SQL DDL | привычен, можно отдать в БД | не выражает кодировки, разделители, маппинг папок, бизнес-правила; парсить DDL — отдельный проект | **экспорт** (и позже импорт как advanced) |
| JSON | машинный | без комментариев, хуже для ручной правки | нет |
| YAML | комментарии | двусмысленный парсинг, тяжёлый | нет |

Вывод: **схема — TOML; SQL DDL генерируется из неё** (кнопка «Экспорт DDL» и
позже «Импорт DDL» с предупреждением, что правила/опции чтения в DDL не
помещаются). В UI пользователь схему **не редактирует текстом** — он правит
таблицу (см. ниже), а TOML остаётся форматом хранения и версионирования.

### 5.2. Экран

```text
┌ sales · Схема ──────────────────────────[Проверить на образце] [Подтвердить]─┐
│ Источник: автоинференс по 3 файлам (0.2 с)       [Переинферить] [Ручная]     │
├──────────────────────────────────────────────────────────────────────────────┤
│ ☰ Колонка      Тип             Nullable  Правила                Файлы        │
│ ≡ id           [i64      ▾]    ☐         3 правила              3/3          │
│ ≡ date         [str      ▾]    ☐         формат даты            3/3          │
│ ≡ amount       [f64      ▾]    ☐         ≥ 0, ≤ 1e9             3/3          │
│ ≡ customer     [str      ▾]    ☑         непусто               2/3 ⚠        │
├──────────────────────────────────────────────────────────────────────────────┤
│ ⚠ Конфликты типов (1)                                                        │
│   amount: ожидаем f64 — в sales_03.csv i64 (320 строк)                       │
│   [Привести к f64] [В карантин строки] [Пропустить файл]                     │
├──────────────────────────────────────────────────────────────────────────────┤
│ Проверка на образце (2 704 строки): ✔ 2 384 пройдут · ⚠ 312 карантин · 8 ошибок│
│   причина: customer пусто (312)                                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

* **Инференс — это предложение**, а не факт: сверху написано, чем он получен
  (сколько файлов/строк), и есть «Переинферить».
* **Редактирование — таблица**, а не текст: тип выбирается из списка
  (i8…i64, u8…u64, f32/f64, bool, str, date, datetime), nullable — чекбокс,
  переименование — по клику, удаление/порядок — drag-handle `≡` (позже).
* **Конфликты** — отдельный блок: что ожидали, что нашли, сколько строк
  затронуто, и три кнопки-решения (по одному на конфликт, не «применить ко всем»).
* **«Проверить на образце»** — обязательный шаг перед подтверждением: сервер
  прогоняет правила на выборке и возвращает числа. Это лучший способ объяснить
  пользователю последствия.
* Подтверждение сохраняет `schemas/<entity>.toml` (с правилами) и переводит
  сущность на стадию 3.

## 6. Стадия 3 — Правила и ограничения (`?tab=rules`)

### 6.1. Набор правил (достаточный и не избыточный)

| Тип | Уровень | Параметры | Куда девается нарушитель |
|---|---|---|---|
| `not_null` | колонка | — | карантин |
| `unique` | колонка/набор | — | карантин (дубликат) |
| `range` | колонка | min, max | карантин |
| `regex` | колонка | шаблон | карантин |
| `date_format` | колонка | формат(ы) | карантин |
| `allowed_values` | колонка | список | карантин |
| `foreign_key` | колонка | сущность + колонка | карантин (позже) |
| `row_count` | таблица | min…max | предупреждение |
| `freshness` | таблица | max возраст по дате | предупреждение |

Severity у каждого правила: **error** (строка → карантин) или **warning**
(строка проходит, но помечается и считается).

### 6.2. Экран

```text
┌ sales · Правила ─────────────────────────[Проверить на образце] [Сохранить]──┐
│ Набор: схемный (хранится в sales.schema.toml)                                │
├──────────────────────────────────────────────────────────────────────────────┤
│ id        not_null(error)  unique(error)              [✎] [✕]               │
│ date      date_format(error, %Y-%m-%d)                [✎] [✕]               │
│ amount    range(error, 0 … 1 000 000 000)             [✎] [✕]               │
│ customer  not_null(warning)                            [✎] [✕]               │
│ + Добавить правило:  колонка [▾]  тип [▾]  ⟶  [Добавить]                     │
├──────────────────────────────────────────────────────────────────────────────┤
│ Образец (2 704 строки): ✔ 2 384 (88%) · ⚠ 312 нарушения (7 причин)           │
│   not_null(customer)        312   [Показать примеры] [Ужесточить до error]   │
└──────────────────────────────────────────────────────────────────────────────┘
```

* Правила добавляются **в контексте колонки** (выбор колонки → тип → параметры),
  а не в отдельном «конструкторе выражений». Никакого free-text SQL.
* Примеры нарушений — сразу в блоке проверки: пользователь видит реальные строки
  и решает, правило неверное или данные грязные.
* Хранение: секция `[[quality]]` в TOML схемы (одна схема = один контракт).

## 7. Стадия 4 — ODS, карантин, передача (`?tab=ods`)

```text
┌ sales · ODS ──────────────────────────────────────────[Запустить прогон ▶]───┐
│ Статус: ✔ готов к отдаче · прогон #12 · 2 мин назад · 23 строки · 3 части    │
│                                                                             │
│ ┌ ODS ────────────────────────┐  ┌ Карантин (312) ───────────────────────┐  │
│ │ data/sales/ods/             │  │ причины:                              │  │
│ │   part-0000.parquet  1.2 МБ │  │  customer пусто        312  [смотреть] │  │
│ │   part-0001.parquet  1.1 МБ │  │  amount < 0              0             │  │
│ │ _manifest.json              │  │ [Скачать карантин (CSV/Parquet)]      │  │
│ └─────────────────────────────┘  └───────────────────────────────────────┘  │
│ [Скачать манифест] [Экспорт DDL] [Скопировать путь ODS]        [Открыть логи]│
└──────────────────────────────────────────────────────────────────────────────┘
```

* **Прогон неизменяем**: каждый запуск создаёт `runs/<run_id>/` (ODS-часть,
  карантин, лог, манифест), а `data/<entity>/ods` — указатель «latest».
  Это даёт воспроизводимость и «откат к прошлому прогону».
* «Готов к отдаче» — это состояние, а не кнопка: зелёная метка появляется,
  когда прогон завершён, ошибок уровня error нет, и манифест записан.
* Карантин — первоклассный артефакт: скачивается, содержит исходные значения,
  причину, имя файла и `row_id`.
* **Манифест** (JSON): части, строки, размеры, min/max по датам, версия схемы,
  хеш правил, `run_id`. Именно это отдают в ODS/DWH и показывают в каталоге.

### Карантин-браузер (`/w/{ws}/quarantine`)

```text
┌ Карантин · sales ────────[причина ▾ all] [файл ▾ all] [🔎 поиск]────────────┐
│ row_id  файл         колонка   значение   причина            действие      │
│ 183921  sales_03.csv customer  ""         not_null           [Исправить ✎]  │
│ 184002  sales_03.csv amount    "240A"     range/invalid_num  [Привести]    │
└─────────────────────────────────────────────────────────────────────────────┘
```

Действия из карантина (по одному, осознанно): «привести к типу» (значение
запомнится как правило преобразования), «подставить значение», «ослабить
правило до warning», «исключить строки». После правки — кнопка **«Перезапустить
с исправлениями»** (новый прогон, старый остаётся).

## 8. Прогон и логи (`/w/{ws}/runs/{run_id}`)

```text
┌ Прогон #12 · sales · ✔ успех · 00:02:14 ────────────────────[Скачать JSONL]┐
│ Фазы:  Чтение ✔ 0:00:41 │ Схема ✔ 0:00:03 │ Правила ✔ 0:01:20 │ Запись ✔   │
│ Файлы: sales_01.csv ✔ 1204→1204 │ sales_02.csv ✔ 1180→1180 │ sales_03.csv   │
│        ✔ 320→312 (8 в карантин: range(amount))                              │
│ Счётчики: 2 704 прочитано · 2 392 в ODS · 312 карантин · 0 ошибок           │
│ Замечания: customer пусто — warning (312)                                   │
└─────────────────────────────────────────────────────────────────────────────┘
```

Логи — структурные (JSONL: фаза, файл, строка, решение, причина, время) плюс
человекочитаемая страница. Из логов всегда понятно: что прочитано, что
отброшено, почему и куда.

## 9. Техника сборки на htmx (чтобы это было просто реализовать)

| Действие | Маршрут | Фрагмент-ответ |
|---|---|---|
| Список сущностей | `GET /w/{ws}` | `hub.html` |
| Сканировать корень | `POST /w/{ws}/scan` | `candidates.html` → `#candidates` |
| Добавить/подтвердить сущность | `POST /w/{ws}/entities` | `entities.html` → `#entities` |
| Перечитать файлы | `POST /w/{ws}/e/{entity}/files/reload` | `files_table.html` |
| Инференс/переинференс схемы | `POST /w/{ws}/e/{entity}/schema/infer` | `schema_table.html` |
| Правка колонки (тип/nullable/имя) | `PATCH`-подобный `POST …/schema/column` | `schema_table.html` |
| Проверить на образце | `POST …/validate?sample=1` | `validation_report.html` |
| Подтвердить схему | `POST …/schema/confirm` | `stage_tabs.html` (статусы) |
| Добавить/править правило | `POST …/rules` | `rules_table.html` |
| Запустить прогон | `POST …/runs` | `job_running.html` (поллинг) |
| Прогресс прогона | `GET /w/{ws}/jobs/{id}` | прогресс → `run_result.html` |
| Карантин | `GET /w/{ws}/quarantine?reason=…` | `quarantine_table.html` |
| Метрики ресурсов | `GET /fragments/resources` | `resources.html` (каждые 2 с) |

Правила: каждый фрагмент — самостоятельный шаблон askama; маршруты — плоские;
поллинг только у прогонов и метрик; тяжёлые шаги (прогон) всегда через
фоновую задачу; кнопки на время операции `disabled` (htmx-класс `htmx-request`).

## 10. Что нужно в данных (за пределами текущей модели)

1. `runs` — таблица в БД: `run_id, workspace, entity, started_at, finished_at,
   status, counts(json), manifest_path, log_path`.
2. `quality` — секция правил в `schemas/<entity>.toml` (см. §6).
3. `runs/<run_id>/` на диске: `ods/*.parquet`, `quarantine/*.parquet`,
   `manifest.json`, `run.jsonl`.
4. `data/<entity>/ods` — указатель на «последний удачный прогон» + `latest`.
5. Каталог (для каталога датасетов и, позже, нод): по манифестам, без чтения данных.

## 11. Порядок реализации UI (после текущего состояния)

| Фаза | Что делаем | Результат |
|---|---|---|
| **UI-1** | Единый каркас: хлебные крошки, табы стадий, статусы-пилюли, страница сущности (пока только `files` + `schema` в режиме просмотра) | пользователь видит путь целиком |
| **UI-2** | Схема: инференс-предложение, таблица-редактор (тип/nullable/имя), конфликты, «проверить на образце», подтверждение | контракт данных зафиксирован |
| **UI-3** | Правила: конструктор в контексте колонки, severity, проверка на образце с примерами | бизнес-проверки созданы |
| **UI-4** | Прогон: фоновая задача, прогресс, страница прогона, лог, ODS + карантин, манифест | «готово к отдаче» |
| **UI-5** | Карантин-браузер и правки с перезапуском; каталог датасетов; `/metrics` в футере уже есть | цикл «нашли проблему → исправили → перезапустили» |

Уже готово из этого: каркас страницы воркспейса, сканирование корня, подтверждение
сущности (схема + привязка), фоновый прогон с прогрессом, метрики, авторизация и
приватные воркспейсы.

## 12. Чего не делаем (анти-примеры)

* **Мастера на 7 шагов** и модалок поверх модалок: стадии — табы одной страницы.
* **Редактора SQL/выражений** для правил: только структурированный конструктор.
* **Автоисправления без показа**: любое «привели к типу» видно в отчёте и логе.
* **Сорока настроек** на воркспейс: три переключателя + параметры в контексте.
* **Клиентского состояния**: никаких «сохранить черновик в браузере» — сервер и
  файлы проекта единственный источник истины.
* **Молчаливых пропусков файлов**: всегда строка в отчёте и в логе.
