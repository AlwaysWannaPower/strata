> Это объяснение для человека, который **учит Rust**, читая код проекта *strata*.
> Мы прошли стадию M0 из `PLAN.md`: собрали workspace из двух крейтов и сделали
> вертикальный срез — CSV можно открыть в окне, посмотреть превью и сохранить

### Зачем workspace из двух крейтов?

`Cargo.toml` в корне описывает не один пакет, а **workspace** — группу пакетов,
которые собираются вместе и могут ссылаться друг на друга по пути:

```toml
[workspace]
resolver = "3"
members = ["crates/strata-core", "crates/strata-app"]
```

Два крейта разделены с **архитектурной** целью, а не из любопытства:

| Крейт | Что это | Кто зависит |
|---|---|---|
| `strata-core` | «движок»: чтение файлов, Polars, запись Parquet | не зависит ни от кого, кроме Polars |
| `strata-app` | «оболочка»: окно, кнопки, показ данных | зависит от `strata-core` |

Почему так: **ядро не должно знать, что существует интерфейс**. Если завтра мы
решим, что UI делается на другом фреймворке, мы перепишем только `strata-app`,
а движок останется нетронутым (и его тесты продолжат работать). Это правило —
«ядро без UI» — зафиксировано в `PLAN.md` как принцип №2.

## 3. Polars: lazy vs eager — главная идея

В `strata-core/src/lib.rs` используется **ленивый** (lazy) путь чтения:

```rust
LazyCsvReader::new(path)     // ещё НИЧЕГО не прочитано
    .with_has_header(true)
    .with_n_rows(Some(n))    // «прочитай максимум n строк»
    .finish()?               // собрать план запроса в LazyFrame
```

`LazyCsvReader` и `LazyFrame` — это **описание того, что нужно сделать**, а не
сами данные. Как рецепт: пока ты не начал готовить, ничего не кипит. Настоящее
выполнение запускает `.collect()`:

```rust
let frame = lazy.collect()?;   // вот теперь Polars реально читает файл
```

Зачем это нужно? Polars может **оптимизировать план** перед выполнением и,
главное, умеет **не читать лишнего**. В `preview_csv` мы ставим
`.with_n_rows(Some(max_rows))` — Polars разберёт только первые `max_rows` строк
файла и остановится. Если бы мы читали «жадно» (eager) весь файл ради показа
50 строк — на файле в 10 ГБ это было бы катастрофой. Уже сейчас код написан
так, как понадобится для больших данных из ТЗ (см. `ТЗ.md` §6 «Приложение не
должно сразу грузить все 50 файлов в RAM»).

### Почему запись пока через collect(), а не поток

В `csv_to_parquet` мы делаем `collect()`, а потом отдаём готовый `DataFrame`
писателю:

```rust
let mut file = std::fs::File::create(parquet_path)?;
let mut writer = ParquetWriter::new(&mut file);
writer.finish(&mut frame)?;   // trait SerWriter — метод из polars::prelude
```

Честно: для маленьких демо-файлов это нормально. Потоковая запись (бить данные
на чанки и писать по частям, не держа всё в памяти) понадобится в M1+, когда
появятся «папка из 50 файлов». Тогда мы перейдём на пофайловую/почанковую
обработку (`PLAN.md` M1, `ТЗ.md` §6). Важно понимать разницу уже сейчас:
`collect()` = «собрать всё в память», потоковая запись = «обработал кусок —
записал — забыл».

## 4. Типы результата: почему UI не видит Polars

Посмотри на публичный API ядра (`strata-core/src/lib.rs`):

```rust
pub struct Preview {
    pub columns: Vec<ColumnInfo>,   // name + dtype (String)
    pub rows: Vec<Vec<String>>,     // каждая ячейка уже строка
}
```

Ядро **не возвращает наружу `DataFrame`** — оно возвращает простые owned-типы
(`String`, `Vec`, числа). Это осознанное решение:

1. **UI не зависит от Polars** (в `strata-app/Cargo.toml` нет Polars — только
   `strata-core`, Dioxus и rfd).
2. Ошибки типов не «протекают» между крейтами — на границе только то, что мы
   сами объявили.
3. Таблицу из `Vec<Vec<String>>` рендерить тривиально.

Внутри ядра ячейки достаются так (`frame_to_preview`): для каждой строки и
каждой колонки вызывается `column.get(i)` — он возвращает `PolarsResult<AnyValue>`
(типизированное значение ячейки), а мы форматируем его через `format!("{value}")`,
потому что у `AnyValue` реализован `Display`. `null` превратится в строку `"null"`.

### Ошибки: единый тип StrataError

Всё, что может упасть, возвращает `Result<T, StrataError>`:

```rust
pub enum StrataError {
    NonUtf8Path(PathBuf),   // Polars хочет пути в UTF-8
    Io(#[from] std::io::Error),
    Engine(#[from] PolarsError),   // ошибка самого Polars
}
```

`#[from]` + `thiserror` дают автоматические конверсии: если внутри функции
встречается `std::io::Error` или `PolarsError`, оператор `?` сам превратит её в
`StrataError`. Код снаружи (UI) видит один тип ошибки и просто показывает
`{err}` в строке статуса — без паник и без знания деталей Polars.

## 5. Анатомия Dioxus-приложения (strata-app/src/main.rs)

Dioxus — это декларативный UI для Rust: ты описываешь, **что** должно быть на
экране, а фреймворк сам обновляет его при изменении состояния. Ментальная
модель знакома тем, кто видел React.

### Точка входа

```rust
fn main() {
    dioxus::LaunchBuilder::desktop().launch(App);
}
```

`LaunchBuilder::desktop()` выбирает десктопную платформу (у нас включена только
она — системный WebView, внутри работает HTML/CSS из нашего `rsx!`). `App` —
корневой компонент.

### Компонент и состояние

```rust
#[component]
fn App() -> Element {
    let mut status = use_signal(String::new);
    let mut preview = use_signal(Option::<Preview>::None);
    // ...
}
```

`use_signal` создаёт **реактивное состояние**: `Signal<T>`. Два способа работы:

| Операция | Код | Смысл |
|---|---|---|
| Прочитать | `preview.read()` | временная ссылка на значение |
| Изменить | `*preview.write() = ...` или `status.set(...)` | поменять значение и **перерисовать** только зависящие части UI |

Когда сигнал меняется, Dioxus перерисовывает компонент, и в разметке
`if let Some(table) = preview.read().as_ref() { … }` автоматически появляется
таблица. Никакого ручного «обнови DOM» — это и есть декларативность.

> Замечание для внимательного читателя: почему `preview` — это
> `Signal<Option<Preview>>`, а не просто `Signal<Preview>` с пустым значением?
> Потому что `Option` честно выражает «данных ещё нет» — и в `rsx!` мы можем
> написать `if let Some(...)`, а не выдумывать «пустую» таблицу.

### События: кнопки

```rust
button {
    onclick: move |_| {
        if let Some(path) = open_csv_dialog() { load_preview(path); }
    },
    "Open CSV…"
}
```

`onclick` — это замыкание, вызываемое при клике. `move` захватывает сигналы
(они `Copy`, поэтому захват дешёвый). Общий код загрузки вынесен в замыкание
`load_preview`, чтобы диалог, кнопка «Load sample» и поле пути вели себя
одинаково.

Текстовое поле:

```rust
input {
    value: path_input,
    oninput: move |evt: Event<FormData>| path_input.set(evt.value()),
}
```

`value` связан с сигналом (поле показывает текущее значение), а `oninput`
обновляет сигнал при вводе. Это «контролируемый input» — состояние живёт в
сигнале, а не в DOM.

### Файловые диалоги

Нативные диалоги открывает крейт **rfd**:

```rust
rfd::FileDialog::new()
    .add_filter("CSV files", &["csv"])
    .pick_file()       // -> Option<PathBuf>; None = пользователь отменил
```

Диалог возвращает `Option<PathBuf>` — отсюда идиома `if let Some(path) = …`.

### Где взять демо-файл без диалога

`sample_csv_path()` ищет `examples/sample_csv/sales_01.csv` относительно
`env!("CARGO_MANIFEST_DIR")` — это **путь к манифесту текущего крейта**,
подставленный компилятором (`crates/strata-app/`), поэтому поднимаемся на два
уровня вверх до корня репозитория. `try_exists()` превращает ошибку пути в
понятное сообщение, а не панику.

## 6. Как запустить

```bash
# первый раз сборка долгая: скачиваются и компилируются сотни крейтов
cd /Users/denisnikulin/Documents/projects/strata

cargo run -p strata-app        # собрать и открыть окно
```

В окне:
1. **Load sample** — открыть демо-файл `sales_01.csv` (или «Open CSV…» — свой).
2. Увидеть таблицу превью (колонки + первые строки).
3. **Save to Parquet** — выбрать место; рядом появится `.parquet`.
4. Внизу — статус: сколько строк и колонок записано.

Тесты ядра (без окна):

```bash
cargo test --workspace
```

Тесты в `strata-core/src/lib.rs` сами создают временный CSV, гоняют
`preview_csv` и `csv_to_parquet`, читают Parquet обратно и проверяют, что
строки/колонки сохранились. Обрати внимание на тест
`missing_file_is_an_error_not_a_panic` — «программа не паникует, а сообщает об
ошибке» здесь проверено как требование, а не как пожелание.

## 7. Словарик (по ходу M0)

| Термин | Что это |
|---|---|
| **Crate** | пакет Rust: библиотека (`lib`) или программа (`bin`) |
| **Workspace** | группа крейтов с общим `Cargo.lock` и одной сборкой |
| **Polars** | библиотека табличных данных для Rust (как pandas, но быстрее) |
| **LazyFrame** | «план запроса»: описание чтения/преобразований без выполнения |
| **eager / lazy** | жадное (сразу всё в память) vs ленивое (по требованию) выполнение |
| **collect()** | материализация: выполнить ленивый план и получить `DataFrame` |
| **DataFrame** | таблица: колонки одинаковой длины; основа Polars |
| **Column / Series** | одна колонка таблицы; у неё есть имя, тип и значения |
| **DataType** | тип колонки: Int64, Float64, String, Date… |
| **Parquet** | колоночный формат хранения на диске (см. `ТЗ.md`) |
| **Dioxus** | декларативный UI-фреймворк для Rust (desktop/web/mobile) |
| **Signal** | реактивное состояние: меняешь — UI перерисовывается сам |
| **rsx!** | макрос-разметка Dioxus (похож на JSX) |
| **Component** | функция, возвращающая `Element` (кусок UI) |
| **rfd** | крейт нативных файловых диалогов |
| **thiserror** | крейт для удобного объявления типов ошибок |

## 9. Дополнение M0.1 — форматы, кодировки, граница staging/ODS

После первого запуска мы расширили «вход» (см. `PLAN.md` M0.1). Что изменилось в коде.

### Новые публичные функции ядра

| Старая (осталась как обёртка) | Новая (основная) | Что делает |
|---|---|---|
| `preview_csv` | `preview_source(path, max_rows)` | превью любого поддерживаемого файла |
| `csv_to_parquet` | `source_to_parquet(path, dest)` | staging любого поддерживаемого файла в Parquet |

У `Preview` и `ImportReport` появилось поле `source: SourceInfo` — «происхождение»
файла: `kind` (CSV/TSV/Parquet и разделитель) и `encoding`. UI печатает его строкой
`CSV · delimiter ';' · windows-1251`, чтобы ты **видел**, как прочитан файл.

### Как работает автоопределение (файл `strata-core/src/lib.rs`)

```text
первые 32 КБ файла
   │
   ├─ magic "PAR1" / расширение .parquet ─► Parquet (Polars scan, без текста)
   │
   └─ текст:
        BOM EF BB BF ─► UTF-8 (BOM)
        BOM FF FE    ─► UTF-16 LE
        BOM FE FF    ─► UTF-16 BE
        строгий UTF-8 ─► UTF-8
        иначе ─► windows-1251 или windows-1252 (кто даст больше кириллицы)
```

- **Разделитель** определяется по первой строке (счётчик `,` `;` `\t` `|` вне кавычек).
- **Чистый UTF-8** читается лениво (`LazyCsvReader`) — масштабируемый путь.
- **Всё остальное** декодируется в UTF-8 (крейт `encoding_rs`) и парсится из памяти
  через `CsvReadOptions::into_reader_with_file_handle(Cursor)` — это почему-то
  обязательный путь: Polars умеет парсить только UTF-8.

> Забавный факт, всплывший в тестах: в `encoding_rs` у `UTF-16LE` **нет кодера**
> (`encode` честно возвращает UTF-8 — так задумано стандартом WHATWG). Для теста
> UTF-16LE-байты мы собираем руками через `encode_utf16()`.

### Почему кодировка — это «сырой» слой, а не ODS

Кракозябры нельзя починить бизнес-правилами: если `ООО Ромашка` приехала в staging
как мусор, никакой regex потом её не восстановит. Поэтому правило проекта
(зафиксировано в `PLAN.md`, принцип 6):

> **Staging (File → Parquet) = достоверный перенос: кодировка, разделитель, типы.**
> **ODS = правила и нормализация: `amount >= 0`, regex, FK, дедупликация.**

В M0.1 мы не применяем ни одного бизнес-правила — только «прочитай файл так, как он
написан». Демо-файл для проверки кириллицы: `examples/sample_csv/russian_cp1251.csv`
(это windows-1251, разделитель `;`).

### Что осталось недоделанным (честно)

- Excel (XLSX) — нужен выбор листа и аккуратная работа с датами: это задача M1.
- Ручной выбор кодировки/разделителя, когда автоопределение ошиблось, — экран Schema (M1).
- Не-UTF-8 файлы декодируются целиком в память: для гигабайтных файлов нужен потоковый
  декодер — в бэклоге (M6+).
