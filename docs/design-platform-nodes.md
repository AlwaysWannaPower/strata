# Дизайн платформы: командный пункт + ноды пользователя (control plane / data plane)

> Ответ на вопрос «как работать с данными, если они десятки-сотни ГБ».
> Коротко: **данные не едут на наш сайт. Едет только метадата и прогресс.**

## 1. Почему не загрузка на сайт

Считать данные на сервере сервиса — значит:

- платить за хранение и трафик чужих гигабайтов;
- быть ответственным за конфиденциальные данные клиента (GDPR/152-ФЗ, утечки);
- упереться в лимиты: один прогон Polars съедает CPU и RAM, десяток
  параллельных пользователей положат инстанс;
- заставлять пользователя дважды гонять данные (к нам и обратно).

Поэтому: **обработка — там, где лежат данные**. Наш сайт — командный пункт.

## 2. Архитектура: control plane / data plane

```text
            ┌────────────────────── STRATA CLOUD (контроль) ──────────────────────┐
            │  axum + htmx         PostgreSQL (пользователи, воркспейсы,        │
            │  web UI              схемы, задачи, манифесты, версии)             │
            └───────────────────────────────┬─────────────────────────────────────┘
                                            │  HTTPS + токен ноды
                                            │  (long-poll / WebSocket)
            ┌───────────────────────────────┴─────────────────────────────────────┐
            │  STRATA NODE (данные) — CLI-агент на машине/кластере пользователя   │
            │  • доступ к локальной ФС (папки-источники)                          │
            │  • движок strata-core: чтение → типы → Parquet                      │
            │  • шифрование кэша/выгрузок                                         │
            │  • докладывает: схема, статистика, прогресс, манифест партиций      │
            └──────────────────────────────────────────────────────────────────────┘
```

Аналоги в индустрии: Dagster/Temporal/Prefect agent, Airbyte workers,
self-hosted runners в GitHub Actions, Tailscale node. Это подтверждённая модель:
контроль централизован, данные — нет.

### Что едет наверх, а что остаётся внизу

| Данные | Где живут | Почему |
|---|---|---|
| Пользователи, аккаунты, воркспейсы | облако (Postgres) | мало по объёму, нужно для UI |
| Схемы (`*.schema.toml`) | облако | это контракт, а не данные |
| Задачи (что, где, когда запустить) | облако | оркестрация |
| Прогресс, логи прогонов | облако (можно урезать) | UI и разбор ошибок |
| Манифест партиций (пути, rows, bytes, min/max) | облако | каталог данных, «что уже готово» |
| **Сырые файлы и Parquet-части** | нода пользователя | объём + приватность |
| Кэш ноды, ключи шифрования | нода (в OS keychain) | не покидают машину |

### Планка «маленькой выборки» для UI

Чтобы превью и схема были видны в браузере, нода отдаёт **образец** (например,
первые 100 строк на сущность + статистика по колонкам). Это килобайты, и это
единственный случай, когда содержимое данных (фрагмент) уходит наверх — при
желании это тоже шифруется ключом пользователя, и тогда превью рендерится в
браузере.

## 3. Протокол ноды (набросок, `/api/v1`)

```text
POST /api/v1/node/register     {node_name, capabilities} → {node_id, node_token}
POST /api/v1/node/heartbeat    {node_id, versions, resources} → {jobs: [...]}
GET  /api/v1/node/jobs?wait=25 long-poll: сервер отдаёт задачу, когда она есть
POST /api/v1/node/jobs/{id}/events  {phase, progress, log_lines}
POST /api/v1/node/jobs/{id}/result  {manifest, schema, sample_rows, stats}
```

Задачи — это уже знакомые шаги нашего пайплайна: `scan_root`, `confirm_schema`,
`stage_entity` (с опциональными параметрами: партиции, каст типов). Нода
выполняет их тем же `strata_core::api`, что и локальный режим — код один.

**Безопасность двусторонняя:**

- нода → сервер: токен ноды (по нему же — tenant: чей воркспейс).
- сервер → нода: **подписанные задачи** (Ed25519). Нода пинует публичный ключ
  сервера, чтобы скомпрометированный контроль не смог выполнить произвольный
  код на машине пользователя. Это обязательное условие модели «мы запускаем
  агент у клиента».
- транспорт — TLS; токены — короткоживущие, с ревокацией.

## 4. Шифрование

- **В транзите**: TLS везде (сайт, нода), HSTS.
- **На ноде (at rest)**: кэш и промежуточные файлы — AES-GCM/age-совместимо,
  ключ в OS keychain. Parquet-датасет остаётся там, где выбрал пользователь
  (обычно на его диске/в его S3).
- **На сервере**: сырых данных нет по определению. Если включаем зашифрованные
  образцы/миниатюры — сервер хранит opaque blob, ключ у пользователя
  (E2E: мы не можем прочитать даже превью, ценой того, что не можем и
  индексировать). Решение по умолчанию: образцы не загружаются, UI просит ноду
  отрисовать превью локально или присылать агрегаты.
- Секреты ноды — не в конфиге, а в keychain/секрет-сторе.

## 5. Продуктовая модель платформы

```text
Аккаунт пользователя
└── Воркспейсы (метаданные в облаке, файлы — у пользователя)
    ├── Entities/схемы (один воркспейс = набор схем)
    ├── Ноды (1..N машин пользователя)
    ├── Задачи и история прогонов
    └── Каталог датасетов (манифесты + ссылки на свои хранилища)
```

Роли: владелец, участники (позже), read-only наблюдатели.
Квоты: число воркспейсов, число нод, объём метаданных, частота прогонов —
именно они, а не гигабайты, становятся тарифной осью.

## 6. Лицензирование (мы хотим закрытую ноду)

Рекомендация: **open core**.

- **Открыто**: ядро (`strata-core`), протокол (спека `/api/v1`), сервер
  (можно AGPL/Apache — решаем позже). Открытая спека нужна, чтобы модель
  «нода у клиента» вызывала доверие и чтобы корпоративный клиент мог аудитить.
- **Закрыто**: нода + облако-функции (мультитенантность, аудит, SSO, лимиты).
- Важно: протокол и ядро открыты → конкуренты могут написать свою ноду; зато
  аудит безопасности и доверие. Компромисс осознанный: закрываем не «формат», а
  сервис.

## 7. Что это значит для кода (шаги)

1. ✅ Пользователи + сессии + приватные воркспейсы (`workspaces/<user_id>/…`).
2. Реестр нод и токены нод (`node_id`, `node_token`, last_seen).
3. Задачи: таблица `jobs` в БД + long-poll выдача ноде; наши web-задачи
   становятся частным случаем (нода «локальная» = сам сервер).
4. CLI `strata-node`: `register`, `run`, `status`; выполняет шаги через тот же
   `strata_core::api`.
5. Подпись задач (Ed25519) + пиннинг ключа сервера в ноде.
6. Шифрование кэша ноды, keychain.
7. Каталог датасетов: манифесты партиций в UI («2.4 ГБ, 12 файлов, min/max по
   дате»), без самих данных.

Пункты 1–3 делают систему функциональной; 4–6 — безопасной для чужих машин;
7 — тем, за что платят.
