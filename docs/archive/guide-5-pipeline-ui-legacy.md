# Гайд 5: единый Pipeline-UI, статус-бар ресурсов и почему workspace больше не «пропадает»

> Обновление интерфейса после M1c (шаги 1–3). Разбор для чтения человеком:
> зачем мы убрали вкладки, как устроено состояние, что показывает нижняя
> панель и как это собрано.

## 1. Было: вкладки-«экраны», каждый сам по себе

До этого шага приложение состояло из отдельных экранов (Sources, Schemas,
Datasets, Project), которые ничего не знали друг о друге:

```text
[Sources]  [Schemas]  [Datasets]  [Project]
   |           |           |           |
свой ввод,  свой ввод,  свой ввод,  свой workspace
своя схема  своя схема  своя схема  (project.toml)
```

Плюс главная боль: **workspace жил внутри экрана Pipeline**. В Dioxus сигнал,
созданный внутри компонента, умирает вместе с компонентом при переключении
экрана — поэтому «создал workspace → переключил вкладку → вернулся → пусто».

## 2. Стало: один Pipeline, состояние живёт в App

Новый каркас (`main.rs`):

```text
┌ topbar ────────────────────────────────┐
│ Strata   [ws: «Продажи 2026» · /path]  │
├ content ───────────────────────────────┤
│   Pipeline (один хаб)                  │
├ statusbar ─────────────────────────────┤
│   «staged sales: …»   CPU 3% · RAM …   │
└────────────────────────────────────────┘
```

Три правила, которые убирают «пропадание»:

1. **Workspace — глобальное состояние App.** Сигнал `ws` (папка + `config`)
   создаётся в корневом компоненте и передаётся вниз. Экран не может его
   потерять, потому что он выше экранов. Модуль `workspace_state.rs` — тонкая
   обёртка: `create` / `open` / `reload` (перечитать `workspace.toml` после
   изменения с диска).
2. **Список последних workspace (`recent.rs`).** При create/open папка
   запоминается в конфиг-директории (`~/.config/strata/recent.txt` на Linux).
   При старте `restore_last()` открывает самый свежий — «всё пропало» не
   наступает даже после перезапуска приложения.
3. **UI = проекция диска.** Карточки, схемы, части датасетов каждый раз
   перечитываются с диска (по сигналу `refresh`, который инкрементится после
   любого действия). UI не может «уехать» от сохранённого состояния.

## 3. Pipeline как хаб: аспекты внутри сущности

Старые экраны не удалены «в никуда» — их функции переехали в контекст
сущности (см. `docs/design-workspace-pipeline.md`, §4):

- **Карточка сущности** — этапы `Sources → Schema → Validate(M3) → Stage` со
  статусами (чипы): привязана ли папка, подтверждена ли схема, есть ли уже
  паркеты в `data/<entity>/`. Клик по карточке открывает/закрывает детали.
- **Детали сущности (`entity_detail.rs`)** — три вкладки, это и есть бывшие
  «экраны», но про одну сущность:
  * *Sources* — файлы привязанной папки (метаданные);
  * *Schema* — сохранённая `schemas/<entity>.toml` (колонки, типы, reader-опции);
  * *Stage / Dataset* — части `data/<entity>/`, комбинированное превью, кнопка
    Stage ▶ (схема-валидированный прогон через `stage_folder_with_schema`).
- **Добавление сущности — mode B**: корень → его подпапки = кандидаты.
  Кандидат ничего не пишет на диск, пока пользователь не нажмёт
  «Confirm schema & bind» в **инспекторе**, где видны колонки, конфликты и
  опции чтения (кодировка/разделитель/заголовок) — то, что умел экран Schemas.

Файлы, которые стали не нужны как отдельные экраны, удалены из навигации
(`sources.rs`, `schema_screen.rs`, `dataset_screen.rs`, `project_screen.rs`);
полезные помощники (маппинг reader-опций, формат байтов, диалоги) переехали
в `util.rs`.

## 4. Нижняя статус-панель: потребляемые ресурсы

Запрос: «тулбар справа внизу, чтобы показывал, сколько ресурсов ест
приложение». Реализация — полноширинная тонкая панель внизу (`footer.statusbar`):

* слева — глобальная строка статуса (последнее действие);
* справа — метрики:
  - **CPU процесса Strata** (%), сглаженный дельтой `utime+stime` из
    `/proc/self/stat` за секунду;
  - **RAM процесса** в МБ и доля от всей памяти (`VmRSS` из
    `/proc/self/status` + `MemTotal` из `/proc/meminfo`);
  - **размер `data/` открытого workspace** (рекурсивный обход, делается
    заново только когда путь поменялся).

### Как это устроено без «магии» (`monitor.rs`)

```text
std::thread (1 раз/сек)                 Dioxus coroutine
┌──────────────────────┐   канал   ┌────────────────────────┐
│ Sampler::sample(dir) ├──────────►│ rx.recv() → sample.set │
└──────────────────────┘           └────────────────────────┘
```

- Обычный поток `std::thread` спит секунду, снимает показания и шлёт структуру
  [`Sample`] в канал (UnboundedSender).
- Dioxus-корутина (`use_coroutine`) принимает и кладёт значение в сигнал
  `sample` — статус-бар перерисовывается раз в секунду.
- Поток ничего не знает о Dioxus; канал — единственная связь. Если корутина
  умрёт (закрытие приложения), `send` вернёт ошибку и поток завершится.
- Никаких async-таймеров и tokio в UI-коде: это проще и не зависит от того,
  на каком рантайме крутится Dioxus.
- Парсеры `/proc` — чистые функции с unit-тестами (см. `#[cfg(test)]` в
  `monitor.rs`). На не-Linux платформах чтение недоступно → метрики показывают
  «—», приложение продолжает работать.

## 5. Карта новых модулей (`crates/strata-app/src/`)

| Файл | Роль |
|---|---|
| `main.rs` | Каркас: глобальные сигналы (`ws`, `status`, `refresh`, `sample`), топбар, статус-бар, весь CSS |
| `pipeline_home.rs` | Хаб: карточки сущностей, mode-B скан, инспектор кандидатов, welcome/recents |
| `entity_detail.rs` | Детали сущности: Sources / Schema / Stage |
| `actions.rs` | Действия над сигналами: open/create/close workspace, save_scan_root, scan_candidates, confirm_and_bind, stage_entity |
| `workspace_state.rs` | `WsCtx {dir, config}` + create/open/reload/restore_last |
| `recent.rs` | Последние workspace (путь, дедуп, cap) |
| `monitor.rs` | Замер CPU/RAM процесса + размер data/ (поток + чистые парсеры) |
| `preview.rs`, `util.rs` | Презентационные таблицы и общие помощники |

## 6. Как проверить руками

1. `cargo run -p strata-app`.
2. Создать workspace → вернуться на страницу «старт» (Close) → открыть из
   «Recent workspaces» — всё на месте.
3. Закрыть приложение и запустить снова — последний workspace открылся сам.
4. Scan root → Inspect… (колонки/конфликты) → Confirm schema & bind →
   карточка появилась → Stage ▶ → в деталях на вкладке Stage видно части и
   превью; внизу справа — CPU/RAM и размер `data/`.
