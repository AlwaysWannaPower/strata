# Guide 1 — Dioxus 0.7 на пальцах: как устроен UI strata (M1a)

> Шпаргалка для человека, который учит Rust + Dioxus, читая код `strata-app`.
> Здесь — не перевод доков, а карта «какая концепция Dioxus где лежит в НАШЕМ
> коде и почему она так работает». Версия Dioxus: **0.7.10** (desktop = системный
> WebView).

---

## 1. Общая картина: что Dioxus делает за тебя

Ты описываешь **что показать**, а не **как обновить**. При изменении состояния
Dioxus перерисовывает затронутые компоненты и сам вычисляет, что поменять в DOM.

```text
Ваши компоненты (функции)
        │  возвращают Element (виртуальное дерево)
        ▼
Dioxus сравнивает новое дерево со старым (diff)
        │
        ▼
меняет только изменившиеся узлы в реальном DOM (WebView)
```

Rust-аналогия: компонент = чистая функция «состояние → разметка»; Dioxus = твой
`diff` + планировщик перерисовки.

---

## 2. Карта нашего кода

```text
main.rs            App (корень)
 ├─ header: бренд + строка «Raw (staging) …»
 ├─ NavRail (активный экран, сигнал)
 └─ main.content: match по Screen
     ├─ Sources   → SourcesScreen        (sources.rs)
     │              ├─ SingleFileCard    (свои сигналы: путь, превью, отчёт)
     │              └─ FolderCard        (свои сигналы: скан, отчёт, превью)
     │                    └─ использует PreviewTable
     ├─ Schema / Datasets / Quality / Logs → PlaceholderScreen (main.rs)
     └─ PreviewTable / PreviewCard       (preview.rs — переиспользуемые)
```

Правило, которое мы соблюдаем: **состояние живёт как можно ниже** — в том
компоненте, который его использует. Наверх (в `App`) поднимаем только то, что
нужно нескольким экранам сразу (сейчас это один сигнал — активный экран).

## 3. Компонент = функция, помеченная `#[component]`

```rust
#[component]
fn SourcesScreen() -> Element {        // нет пропсов — пустые скобки
    rsx! { div { class: "screen", … } }
}
```

Компонент с входными данными получает **props-структуру**:

```rust
#[derive(Props, Clone, PartialEq)]     // derive превращает struct в пропсы
struct PreviewCardProps {
    title: String,                     // поле = пропс, задаётся у вызывающего
    table: Preview,
}

#[component]
fn PreviewCard(props: PreviewCardProps) -> Element {
    rsx! { div { … "{props.title}" … } }
}
```

Вызов из другого компонента — как HTML-тег с пропсами:

```rust
PreviewCard { title: table.source.summary(), table: table.clone() }
```

Почему `Clone + PartialEq`: Dioxus **пропускает перерисовку**, если пропсы не
изменились (сравнение через `PartialEq`). Поэтому пропсы дешево сравнивать.

> Нюанс 0.7: имя компонента = имя функции (`PreviewCard`), а структура пропсов
> обычно называется `<Имя>Props` и лежит рядом. Функция должна быть `pub`,
> чтобы её можно было вызывать из другого модуля.

## 4. Элементы: `rsx!` — разметка внутри Rust

Макрос `rsx!` выглядит как JSX/HTML, но это настоящий Rust-код:

| Синтаксис | Что делает | Пример в коде |
|---|---|---|
| `div { … }` | HTML-элемент (строчные = теги) | везде |
| `"{выражение}"` | **динамический текст** (форматируется как текст) | `td { "{cell}" }` |
| `{выражение}` | выражение-ребёнок | `document::Style { "{CSS}" }` |
| `for x in list { … }` | цикл → N детей | строки таблицы |
| `if cond { … }` | условный рендер | `if preview.read().is_some()` |
| `if let Some(t) = … { … }` | условный рендер с разбором `Option` | карточка превью |
| `match x { … }` | переключение экранов | в `App` |
| `class:` | атрибут class (динамический) | подсветка активной вкладки |
| `onclick:`, `oninput:` | обработчики событий | кнопки, поле пути |

**Динамический текст в кавычках — это format-string.** `"{report.rows}"`
превращается в текст автоматически (нужен `Display` у типа — у чисел и строк он
есть). Отсюда правило: писать `td { "{cell}" }`, а не `td { cell }` — второй
вариант для `String` не соберётся.

`document::Style { "{CSS}" }` в `App` вставляет один общий CSS в `<head>`
страницы WebView (в 0.7 это компонент `document::Style`, а не тег `<style>`).

## 5. Состояние: `Signal<T>` и хук `use_signal`

```rust
let mut status = use_signal(String::new);               // String
let mut preview = use_signal(|| Option::<Preview>::None); // Option<T>
```

Два жёстких факта API 0.7 (мы обожглись на обоих):

1. `use_signal` принимает **замыкание**, а не значение:
   `use_signal(|| 0)` ✓, `use_signal(0)` ✗.
2. Хуки (`use_signal` и другие `use_*`) можно вызывать **только на верхнем
   уровне тела компонента**, не внутри `if`, циклов или замыканий. Это
   гарантирует стабильный порядок состояний между перерисовками.

`Signal<T>` — умный указатель с двумя режимами доступа:

```rust
// Чтение: временная ссылка. Пока живёт ссылка, писать нельзя.
let rows = preview.read().as_ref().map(|p| p.rows.len());

// Запись — три эквивалентных способа:
status.set(String::from("ok"));          // заменить целиком
*status.write() = String::from("ok");    // write() даёт &mut T
```

Любая запись **помечает компонент грязным**, и Dioxus перерисует его. Именно
поэтому «просто присвоил сигналу» достаточно, чтобы таблица появилась.

Типичный паттерн «данных ещё нет» — `Option`:

```rust
if let Some(table) = preview.read().as_ref() {
    PreviewCard { … }   // отрисовать, только когда данные загружены
}
```

`Signal` — **Copy**: можно раздавать копии направо и налево (в пропсы, в
замыкания) — это дёшево, все копии указывают на одно состояние.

## 6. События: замыкания с `move`

```rust
button {
    onclick: move |_| {
        if let Some(path) = open_file_dialog() {
            path_input.set(path.display().to_string());   // сигнал из захвата
        }
    },
    "Browse…"
}
```

- `onclick` — обработчик. Dioxus зовёт его при клике, передавая `Event`.
- `move` обязателен: замыкание переживает текущий вызов компонента (хранится
  в обработчике), поэтому захватывает переменные по значению. `Signal` — Copy,
  захват дешёвый.
- Текстовое поле — «контролируемый input»: значение берётся из сигнала, а
  `oninput` пишет обратно:

```rust
input {
    value: path_input,                                  // показать текущее
    oninput: move |evt: Event<FormData>| path_input.set(evt.value()),
}
```

Состояние живёт в сигнале, а не в DOM, — поэтому им могут пользоваться другие
части UI (например, кнопка «Open» читает то же поле).

### Логика-обработчики: замыкания внутри компонента

Общий код действия выносится в замыкание рядом с состоянием:

```rust
let mut import_from = move |path: PathBuf| {
    match preview_source(&path, PREVIEW_MAX_ROWS) { … }
};
```

Несколько кнопок вызывают одно и то же `import_from` — один код, одно
поведение, меньше расхождений.

## 7. Пропсы-сигналы: навигация без «пробрасывания колбэков»

В веб-фреймворках для «дочерний → родитель» обычно нужны колбэки. В Dioxus мы
можем передать **сам сигнал**:

```rust
#[derive(Props, Clone, PartialEq)]
struct NavRailProps {
    active: Signal<Screen>,   // Copy → передаётся по значению
}

#[component]
fn NavRail(props: NavRailProps) -> Element {
    let mut active = props.active;               // вытащили из props
    button {
        onclick: move |_| active.set(screen),    // «родитель» узнает сам
        …
    }
}
```

> Нюанс: `Signal::set` требует `&mut self`, поэтому локальную копию объявляем
> `let mut active = …` — иначе компилятор скажет «cannot borrow as mutable».

---

## 8. Что НЕ входит в M1a (и почему не паникуем)

- **Async-загрузка с прогрессом**: сейчас файлы маленькие, синхронно нормально.
  Для больших данных в M4 появится `spawn`/`use_resource` и отмена прогона.
- **Виртуализация таблицы**: 50 строк превью — обычный `<table>`; миллион строк
  потребует виртуализации (M4).
- **Глобальный стор**: пока общий только активный экран; история «Logs» в M4
  поднимет общий сигнал в `App`.
