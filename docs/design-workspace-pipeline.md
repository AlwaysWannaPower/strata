# Дизайн: Workspace + единый пайплайн («интерфейс агентов»)

> Решение по продукту (сессия после M1b). Цель: сделать из набора вкладок
> **один интуитивный пайплайн** вокруг workspace, чтобы между шагами
> чувствовалась связь и общее состояние. Вторичные цели: удобный UI,
> экономичный движок, минимальное потребление ресурсов.

---

## 1. Workspace — аналог проекта IDE

```text
<workspace>/
├── workspace.toml        ← имя, версия, корень data/, список sources
├── schemas/              ← *.schema.toml (пользовательские или подтверждённые авто)
├── plugins/              ← зарезервировано: «функции/плагины» (сейчас пусто)
├── logs/                 ← история прогонов (позже)
└── data/                 ← сюда пишутся паркеты (путь настраивается)
```

- **Список workspace** (create/open) — как список проектов в IDE; текущий
  workspace — глобальное состояние приложения (как сейчас signal «проект»,
  но с полным контекстом: источники, схемы, датасеты).
- Открыв workspace, мы **подгружаем настройки**: схема-ридеры, маппинг
  «папка → сущность», позже — плагины.
- Миграция: текущий `project.toml` становится `workspace.toml` (поле `name`,
  `version`, плюс `data_dir`); сохранённые схемы уже TOML — переносятся без
  изменений.

## 2. Сущность и правило «одна папка = одна схема»

Сущность (entity) = логическая таблица (`sales`, `clients`, `products`).

Правило: **все файлы одной сущности живут в своих папках и обязаны
соответствовать одной схеме**. Два способа задать привязку:

**Режим A — явный (сущность → папка):**
пользователь называет сущность и указывает папку. Всё, что найдено в папке,
читается как `sales`. Файл, не подходящий под схему, — ошибка/карантин (M3),
но никогда не «догадка».

**Режим B — скан корня (корень → подпапки = сущности):**
пользователь даёт общий корень. Сканируются **только подпапки 1-го уровня**
(вложенность запрещена): N подпапок = N кандидатов сущности, в каждой —
неопределённое число файлов одной схемы. Имя подпапки → имя сущности
(уточняется пользователем).

Оба режима приводят к одному внутреннему представлению:

```rust
SourceBinding {
    entity: String,            // "sales"
    folder_mode: FolderMode,   // ExplicitFolder(path) | RootScan(root)
    schema: Option<SchemaFile>,// подтверждённая или auto
}
```

## 3. Схема

**Формат: `*.schema.toml`** (решение). Сравнение и обоснование — в
`PLAN.md`/этом документе:

- SQL DDL — не источник: не умеет настройки чтения, маппинг, DQ-правила.
  SQL генерируется из схемы для ODS/БД.
- JSON — без комментариев, хуже для людей.
- YAML — сложный и двусмысленный парсинг.
- **TOML** — комментарии, строгий, отлично парсится `serde+toml` (уже в стеке),
  уже используется для проекта.

Пример `sales.schema.toml`:

```toml
# sales.schema.toml
schema_version = 1
entity = "sales"

[reader]                 # как читать файлы этой сущности
delimiter = "semicolon"  # auto/comma/semicolon/tab/pipe
encoding = "cp1251"      # auto/utf8/cp1251/cp1252/utf16le/utf16be
has_header = true

[[columns]]              # порядок важен
name = "id"
type = "i64"
nullable = false

[[columns]]
name = "date"
type = "str"

[[columns]]
name = "amount"
type = "f64"
# quality rules появятся в M3 (>= 0 и т.д.)
```

Откуда берётся схема:
1. **Пользователь создал сам** → она в `schemas/`.
2. **Авто-инференс**: читаем файлы (существующий `schema_from_folder`),
   показываем предложение (колонки/типы/конфликты), пользователь
   подтверждает или правит → сохраняем как `*.schema.toml` и привязываем к
   папке. Сохранённая схема — источник истины для следующих прогонов.

## 4. «Интерфейс агентов»: единый пайплайн вместо вкладок

Главный экран — **Pipeline (Workspace)**. Одна сущность = одна карточка с
состоянием на каждом этапе:

```text
[1 Sources] → [2 Schema] → [3 Validate] → [4 Stage]
   │             │             │             │
   выбор папки   схема: есть?   (M3: правила,  Stage: папка → parquet
   / корня       авто vs ручная  карантин)     в workspace/data/<entity>/
```

Состояние карточки видно сразу: что привязано, подтверждена ли схема,
сколько файлов, был ли прогон, есть ли проблемы. Клик по карточке открывает
детали (файлы/превью/схему/отчёт) — те самые «экраны», но уже **в контексте
сущности**, а не отдельные вкладки.

Топбар: выбор/создание workspace + общий статус (схем подтверждено X/N,
диск, последний прогон). Правый сайдбар — второстепенное: Datasets, Logs.

Сценарий будущих версий, который дизайн держит в голове:
> дал источник → загрузка → договорились о схеме → авто-конверт в parquet
> (или сразу в БД).

## 5. Принципы реализации (оптимизация)

- Движок остаётся без UI; UI подписан на одно состояние workspace.
- Никаких повторных полных чтений: превью ≤ N строк, инференс на выборке,
  stage — потоковый/пофайловый с прогрессом (M4).
- Схемы кэшируются в памяти при открытии workspace; диск читается при
  изменениях только для затронутых сущностей.
- Один источник правды на каждый вопрос: файлы схем — источник типов;
  датасеты в `data/<entity>/` — результат stage.

## 6. Что строим по шагам (M1c)

1. Модель workspace: `workspace.toml` (name, data_dir), список workspace
   (недавние + create/open), миграция «project» → «workspace».
2. `SourceBinding`: режимы A/B + сканер корня (подпапки 1-го уровня) +
   инференс с подтверждением и сохранением `*.schema.toml`.
3. Pipeline-UI: workspace switcher + карточки сущностей + навигация в
   контексте сущности (файлы/превью/схема/отчёт), stage в `data/<entity>/`.
4. Затем Validate (M3) и история прогонов в `logs/`.
