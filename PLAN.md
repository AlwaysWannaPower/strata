# PLAN — strata (Data Engineering Workbench)

> Контекст: учебный проект. Владелец учит Rust и инженерию через **агентную разработку**:
> работу выполняют агенты с высокой экспертизой, человек учится, читая код и документацию.
> Классические оценки «по неделям» не применяются — план постадийный: каждая стадия даёт
> работающий вертикальный срез и заканчивается разжёванной документацией.

Источник требований: `ТЗ.md`. Продукт по ТЗ — **локальный Data Engineering Workbench**:

> «Дал программе папку с грязными CSV/XLSX/Parquet файлами → она определила структуру →
> я подтвердил схему → она провалидировала → объединила → получил нормальный Parquet Dataset
> и увидел проблемы».

---

## 0. Вердикт по реализуемости (кратко)

| Ось | Оценка |
|---|---|
| Ядро + флоу данных (Rust + Polars → Parquet Dataset) | **Реализуемо хорошо.** Стек зрелый: Dioxus 0.7 стабилен, Polars в Rust — продакшн-библиотека. Самые кропотливые места: карантин ошибочных значений, Excel-чанкинг, прогресс/отмена. |
| Красивый и удобный интерфейс | **Достижимо** (потолок = HTML/CSS), но это самый дорогой блок (30–40% бюджета). Главный техриск — виртуализированная таблица-грид. Ядро держим независимым от UI. |
| Desktop vs Web | **Desktop-first.** WASM-версия упирается в лимиты браузера (много-гигабайтные файлы невозможны). Web-тир — в конец бэклога. |
| Open Source | Реалистично. Рекомендация: **лицензия MIT** (см. §7). Реальная цена — не код, а упаковка и документация. |
| Спрос в 2026 | Ниша реальная, массового рынка нет. Категория плотная (OpenRefine, KNIME, Alteryx/Trifacta, Tableau Prep, DuckDB-инструменты), но ровно ниши «локальный file→Parquet, project-based» никто не занимает. Выигрывает скорость сценария и DX, а не «ещё один ETL». |

## 1. Принципы

1. **Вертикальные срезы.** Каждая стадия заканчивается работающим демо: `cargo run` открывает
   окно и делает сквозной сценарий. Никаких «этапов только для ядра без UI» после M1.
2. **Ядро без UI.** Крейт `strata-core` не зависит от Dioxus. Даже если UI-фреймворк не подойдёт,
   движок живёт отдельно и тестируется без окна.
3. **Каждая стадия = код + документация.** Требование к качеству кода:
   - `///`-док-комменты на каждом публичном типе/функции: **что делает, почему, инварианты**;
   - `//!`-шапки модулей: зачем модуль, как вписан в поток;
   - код пишется «разжёванно»: читаемый, без магических однострочников;
   - после стадии — `docs/guide-N-*.md`: объяснение сценария по-русски, со схемами и «почему так».
4. **Desktop-first.** Веб — только в открытом бэклоге.
5. **Никакого оверинжиниринга.** Сначала простая, явная архитектура. Рефакторинг — когда
   появятся реальные боли, а не заранее.
6. **Граница staging/ODS** (важно для ТЗ). Первый перенос (File → Parquet Dataset) — это
   «сырой» слой: мы **достоверно переносим** данные — правильная кодировка (без кракозябр),
   разделитель, заголовки, типы по инференсу — но **не исправляем значения**. Бизнес-правила
   (`amount >= 0`, regex, FK, дедупликация, форматы) и нормализация «под ODS» — это слои
   Validate/Normalize **после** staging. Кодировка — часть сырого слоя: если мусор попал в
   staging, никакие правила его потом не починят.

## 2. Предлагаемая структура репозитория

```text
strata/
├── Cargo.toml            # workspace
├── PLAN.md               # этот файл
├── ТЗ.md
├── docs/                 # разжёванные гайды по стадиям
├── crates/
│   ├── strata-core/      # модель предметной области + движок + хранилище (БЕЗ UI)
│   │   └── src/
│   │       ├── model/    # Project, Source, FileMeta, Schema, Dataset, ...
│   │       ├── engine/   # scan → infer → validate → normalize → sink
│   │       └── storage/  # layout проекта на диске (см. ТЗ §10)
│   └── strata-app/       # Dioxus Desktop UI (bin)
│       └── src/
└── examples/             # демо-данные (грязные CSV/XLSX/Parquet) для проверок
```

`crates/strata-core` — библиотека. `crates/strata-app` — бинарь Dioxus 0.7 (desktop, webview).
CLI-обёртка не обязательна на старте: тесты ядра и UI-кнопки покрывают сценарии.

## 3. Стадии

Каждая стадия: **цель → сценарий (демо) → что делаем → что изучаем из Rust →
критерий готовности → документация**.

### M0 — Спайк «CSV в окно и в Parquet»

**Цель:** доказать, что Dioxus 0.7 + Polars + Parquet сходятся в одном бинарнике, и собрать
скелет workspace.

**Сценарий:** `cargo run -p strata-app` открывает окно; в нём кнопка «Открыть CSV» → таблица
на 50 строк из CSV → кнопка «В Parquet» → рядом с файлом появился `out.parquet`.

**Что делаем:**
- workspace из двух крейтов (`strata-core` пока пустой-заглушка, `strata-app`);
- в `strata-app`: Dioxus desktop, file-dialog, рендер простой таблицы;
- в `strata-core`: первая функция `csv_to_parquet(path)` через Polars (lazy → sink).

**Что изучаем:** workspace и зависимости, `Result`/`?`/`anyhow`, основы Dioxus (компонент,
событие, состояние), основы Polars (`LazyFrame`, `sink_parquet`), `std::fs`.

**Критерий готовности:** окно открывается, CSV показывается, parquet пишется, `cargo test` зелёный.

**Документация:** `docs/guide-0-skelet.md` — «как устроен репозиторий», как запускать,
карта крейтов, объяснение Polars lazy vs eager простыми словами.

### M0.1 — Многоформатность и кодировки «сырого» слоя (сделано)

Быстрый фикс по обратной связи: расширен вход и починены кракозябры ещё до M1.

**Что добавили:**
- форматы: разделители `,` `;` `\t` `|` (автоопределение по первой строке) + Parquet;
  Excel (XLSX) — сознательно в M1 (нужен выбор листа и свой инференс дат);
- кодировки: UTF-8 (с/без BOM), UTF-16 LE/BE (BOM), windows-1251, windows-1252
  (автоопределение: BOM → строгий UTF-8 → эвристика кириллицы 1251/1252);
  ручной выбор кодировки/разделителя — в M1 (экран Schema);
- UI: единый виджет источника (поле + Browse… + Open + Load sample), строка
  provenance «формат · разделитель · кодировка»; без дублирующих кнопок «открыть»;
- пример `examples/sample_csv/russian_cp1251.csv` для ручной проверки;
- ядро: `preview_source` / `source_to_parquet` (обобщённые), `preview_csv` /
  `csv_to_parquet` остались тонкими обёртками; тесты 8 шт.

**Ограничение (честно):** для не-UTF-8 файлов декодируем целиком в память (малые файлы);
потоковое декодирование больших файлов — в M6+.

### M1a — Источник-папка + UI-каркас (сделано)

Первая часть M1, сделанная с акцентом на UI (обучение Dioxus 0.7) и подробные
комментарии в коде (см. `docs/guide-1-dioxus.md`).

**Ядро (`strata-core/src/folder.rs`):**
- `scan_folder` — список файлов папки (имя, размер, грубый тип) без чтения данных;
- `folder_to_parquet` — staging папки: каждый файл → `NNNN-<stem>.parquet` часть
  в каталог-датасет; файлы неизвестных типов и файлы с ошибками не роняют прогон —
  они попадают в отчёт (`skipped`), успешные — в `staged` (ETL-семантика);
- `preview_parts` — объединённое превью датасета (склеиваются только части с
  одинаковыми колонками).

**UI (`strata-app`):** каркас приложения: шапка + навигация (Sources / Schemas /
Datasets / Quality / Logs) на enum `Screen` + экраны-заглушки; экран Sources:
карточка «один файл» + карточка «папка» (скан → список → stage → превью датасета
+ отчёт); модули `main.rs` / `sources.rs` / `preview.rs`; Dioxus-концепции
разжёваны в комментариях и в гайде.

**Тесты:** 10 (добавлены: скан папки, staging с пропуском «мусорного» файла,
превью датасета из частей).

**Остаток M1 (M1b):** ✅ *Reader Options* (кодировка/разделитель/«первая строка —
заголовки»: `ReaderOptions.has_header`, чекбокс в UI). ✅ *Инференс схемы*:
`strata-core/src/schema.rs` (`schema_from_file` / `schema_from_folder` — колонки+типы,
конфликты типов между файлами, отсутствующие колонки, failed), экран Schemas в UI
(файл или папка, reader-опции). ✅ *Партиции и Datasets-экран*: `source_to_parquet_partitioned` (Hive-папки
`col=value/…` для строковой колонки), `folder_to_parquet_partitioned`,
`list_parts`/`preview_parts` (рекурсивно), экран Datasets (части + превью);
UI Folder-карточки получил опцию «Partition column». ✅ *Схема-валидированный stage* (`stage_folder_with_schema`): файлы читаются
по опциям схемы и сверяются с подтверждённой схемой (имена/порядок/типы);
несоответствие → skipped с причиной, а не слепой stage. `scripts/check.sh`
(fmt+test+check). Продолжение: применение каста типов при полном чтении.
✅ *project.toml* (`strata-core/src/project.rs`): create/open проекта
(`project.toml` + `schemas/` + `logs/`), сохранение/загрузка/список схем
(колонки + reader-опции токенами), тесты; экран Project в UI; Schemas →
«Save schema to project»; общий сигнал проекта в App (переживает навигацию;
файлы — на диске, переживают перезапуск). Осталось: применение схемы при
stage (cast к типам), Excel (XLSX), история прогонов в Logs.

### M1c — Workspace + единый пайплайн («интерфейс агентов», сделано)

Полный дизайн: `docs/design-workspace-pipeline.md`. Ключевые решения:
- **Workspace** (как проект IDE): `workspace.toml` + `schemas/` + `data/`
  (сюда паркеты) + `plugins/` + `logs/`; список workspace (create/open),
  текущий workspace — глобальное состояние.
- **Формат схемы — TOML** (`*.schema.toml`): колонки+типы+nullable, опции
  чтения, маппинг; SQL DDL генерируется из схемы для ODS/БД.
- **Правило «одна папка = одна схема»**: режим A (явная сущность → папка)
  и режим B (корень → подпапки 1-го уровня, каждая = сущность); без схемы —
  авто-инференс с подтверждением и сохранением.
- **UI = единый пайплайн**: главный экран Pipeline (этапы Sources → Schema →
  Validate → Stage), карточка на каждую сущность с её состоянием; вкладки
  становятся стадиями в контексте сущности.

**Сделано (шаги 1–3 M1c):**
- ✅ Модель workspace (`workspace.rs`) + global state в `App`: workspace
  **переживает навигацию** (живёт не в экране) и **восстанавливается при
  старте** из списка последних (`recent.rs`); недавние — на стартовом экране.
- ✅ Единый Pipeline-хаб вместо разрозненных вкладок: экраны
  Sources/Schemas/Datasets/Project удалены из навигации; их функции живут в
  контексте сущности (карточки с этапами Sources → Schema → Validate(M3) →
  Stage; детали сущности: файлы / схема / датасет+превью).
- ✅ Mode B с честным инспектором: перед подтверждением видно колонки и
  конфликты + reader-опции (encoding/delimiter/header); подтверждение =
  save schema + binding; stage = **schema-validated** (`stage_folder_with_schema`).
- ✅ Нижняя статус-панель на всю ширину: слева — статус, справа — потребление
  ресурсов процесса Strata (CPU %, RAM МБ/% от общей) и размер `data/`
  workspace; опрос раз в секунду фоновым потоком (`monitor.rs`, `/proc`, Linux).
  Устройство UI — `docs/guide-5-pipeline-ui.md`.
- Осталось из M1c: режим A в UI, Validate (M3), история прогонов в `logs/`.

### M1 — Вертикальный срез MVP (однородные CSV)

**Цель:** главный сценарий ТЗ для одного случая: **папка CSV → инференс схемы → подтверждение →
Parquet Dataset → итоги**. Всё сквозь UI.

**Сценарий:**
1. Создать проект (имя, путь) → появился каталог проекта по layout ТЗ §10 (`project.toml`,
   `data/processed/…`).
2. Добавить источник «Продажи» — выбрать папку с CSV.
3. UI показывает: 20 файлов, их метаданные (строки, размер), кнопка «Определить схему».
4. Схема: колонки + типы (auto из Polars) — показываем таблицей, подтверждаем.
5. «Создать датасет» → прогресс по файлам → `data/processed/sales/` с партициями → итоги
   (файлов, строк, объём).

**Что делаем:**
- `strata-core::model`: `Project`, `Source`, `FileMeta`, `ColumnSchema`, `Dataset`;
- `strata-core::storage`: создание проекта, чтение/запись `project.toml` (serde + toml);
- `strata-core::engine`: `scan` (обход папки, метаданные), `infer_schema` (первый файл или
  выборка), `build_dataset` (ленивый прогон всех файлов → sink в партиционированный каталог,
  прогресс по файлам);
- `strata-app`: экраны Проект → Источник → Схема → Прогон (пока без pipeline-view, просто шаги).

**Что изучаем:** serde (struct + rename, ошибки), `std::path`/`PathBuf`, итераторы, traits на
практике, разделение model/storage/engine, тесты через golden-files (фикстуры в `examples/`).

**Критерий готовности:** сквозной сценарий работает на демо-папке; результат читается Polars
обратно с той же схемой; тесты ядра покрывают scan/infer/build.

**Документация:** `docs/guide-1-slice.md` — «что происходит при импорте» (диаграмма потоков),
объяснение Parquet Dataset и партиций, разбор каждого модуля ядра с примерами структур.

### M2 — Многоформатность, конфликты схемы, ручная схема

**Цель:** источник из Parquet и XLSX; **инференс схемы по всем файлам**; показ конфликтов
(Expected / Found / Files affected) с действиями; ручное редактирование схемы.

**Сценарий (добавка к M1):**
- папка со смешанными форматами или XLSX-папка (читаем первый лист);
- один файл с `amount: String` среди `Float64` → UI показывает конфликт, предлагает
  «Игнорировать файл» / «Конвертировать» (реалистично на этом этапе: «Игнорировать» и
  «Конвертировать в Float64» для чисел со строгим кастом; невалидные значения в карантин — M3);
- ручное изменение типа колонки в схеме сохраняется в проект.

**Что делаем:**
- чтение Parquet и XLSX (через Polars/calamine);
- `infer_schema` по всем файлам → общая схема + список расхождений по файлам;
- стратегии разрешения конфликтов как enum в ядре (решения принимает UI, применяет ядро);
- сохранение схемы в `project.toml`, повторное использование при прогонах.

**Что изучаем:** enums с данными (`ConflictResolution`, `SchemaDiff`), работа с большими
коллекциями, формат-диспетчеризация (`match` по расширению + трейт `FileReader`), Polars:
`read_excel`, приведение типов (`cast strict=false`).

**Критерий готовности:** демо-папки из `examples/` со смешанными типами проходят сценарий;
конфликты видны и разрешаются; схема переживает перезапуск приложения.

**Документация:** `docs/guide-2-formats.md` — обзор форматов (CSV/XLSX/Parquet, когда какой),
«как устроен инференс», примеры конфликтов и их моделирование.

### M3 — Data Quality и Quarantine (самый сложный модуль)

**Цель:** правила качества и **карантин проблемных строк** — то, что делает продукт «настоящим».

**Сценарий:** после подтверждения схемы прогон проходит валидацию:
- правила: `NOT NULL`, `UNIQUE`, `RANGE` (напр. `amount >= 0`), `REGEX`, `DATE FORMAT`, `TYPE`;
- итог: «✓ 1 284 392 rows, ⚠ 23 duplicate IDs, ⚠ 7 invalid dates»;
- проблемные строки пишутся в `data/quarantine/<dataset>/<reason>/` (см. ТЗ §9) с указанием
  `row_id`, значения, ожидаемого типа и причины;
- экран «Проблемы»: список причин → по клику примеры строк из карантина.

**Что делаем:**
- модель правил (`QualityRule` enum + параметры), редактор правил в UI (минимум: список
  правил на колонку);
- движок валидации: детекция невалидных значений **до** приведения типов, чтобы карантин
  ловил именно `"240A"`, а не молчаливый null (подзадачи см. ниже);
- запись valid / quarantine двумя потоками; связь строки с файлом/row_id.

**Подзадачи (разбить отдельно, это ядро всей сложности):**
- P1: модель правил + сериализация в схему;
- P2: пассы детекции ошибок по типам (number/date/string/unique);
- P3: запись карантина с причинами;
- P4: сводка «Data Quality»;
- P5: UI-экран проблем.

**Что изучаем:** паттерн «валидатор как цепочка пассов», работа с null vs ошибкой
(Option/Result и полиморфные колонки), пакетная обработка, unit-тесты на грязных фикстурах.

**Критерий готовности:** каждая фикстура в `examples/dirty/` даёт ожидаемый отчёт и карантин;
ни одна валидная строка не теряется (свойство: valid + quarantine == total).

**Документация:** `docs/guide-3-quality.md` — «как устроена валидация»: почему карантин
отдельно от схемы, модель причины ошибки, гарантия non-loss.

### M4 — UI-полировка и флоу вокруг pipeline

**Цель:** интерфейс уровня ТЗ §12 и §5: навигация слева (Sources/Schemas/Datasets/Quality/Logs),
pipeline-вид со степенями Folder → Polars → Schema → Parquet, вкладки Files/Preview/Schema,
прогресс и отмена прогона, тёмная тема.

**Что делаем (по под-этапам):**
- U1: каркас экранов и навигация, тёмная тема + дизайн-токены;
- U2: pipeline-вид: степени кликабельны, состояние (ожидает/идёт/ок/ошибки), переходы;
- U3: вкладка Preview: **виртуализированный грид** (главный техриск UI) + семплирование
  (`head`), а не полная загрузка;
- U4: вкладка Schema: таблица колонок с типами/правилами и inline-редактированием;
- U5: прогресс и отмена прогона (события из ядра), логи в `logs/`;
- U6: экран Quality/Problems из M3.

**Критерий готовности:** сценарий M1+M3 целиком проходится в окне без консоли; прогон на

## 5. Правила работы агентов (важно для агентной разработки)

1. Каждый PR/шаг: код + тесты + **документация** (см. §1.3) — иначе шаг не завершён.
2. Названия, комментарии, док-строки — на английском (стандарт индустрии, часть обучения);
   объяснительные гайды в `docs/` — на русском, «для чтения человеком».
3. Никакого «магического» кода: сложное выражение → именованная функция с док-строкой.
4. Перед рефакторингом — мотивация одной строкой в коммите.
5. Демо-данные всегда в `examples/`, генерируются скриптом/фикстурой, чтобы можно было
   воспроизвести грязные случаи.

## 7. Про лицензии (коротко, для владельца)

- **MIT** — самая простая: разрешает всем использовать/менять/продавать код с указанием
  авторства. Ноль обязательств, ноль риска. **Рекомендация для этого проекта.**
- Apache-2.0 — тоже разрешительная, чуть длиннее, добавляет явную патентную грамоту.
- GPL — копилефт: кто встроит код в закрытый продукт, обязан открыть свой. Для инструмента,
  который встраивают в рабочие процессы, часто отпугивает компании.
- Вывод: на этапе обучения и «доведу — уже победа» берём **MIT**: одной строкой в LICENSE,
  ничего не блокирует, ничего не обязывает. Открытый исходник при этом остаётся открытым даже
  если проект заброшен — а это и есть страховка от «зря делал».
